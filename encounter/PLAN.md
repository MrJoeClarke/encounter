# Encounter: World Building for TTRPGs

A multiplatform (macOS, iOS, iPadOS) SwiftUI app for building and browsing campaign worlds. D&D 5e comes first. The design keeps other systems easy to add.

## 1. Goals (v1)

1. Typed information pages: Character (playable / NPC / monster), Place, Event, Item, Organisation, Race/Species/Ancestry.
2. Each type has its own attributes. Choosing a rule system adds that system's attributes.
3. Pages link to each other, including inline `@` mentions.
4. Places form a hierarchy (region, settlement, building).
5. Upload a map image, show it interactively, and pin places on it.
6. Events are either backstory or part of a campaign. Linked events produce timelines and character movement.
7. Search across everything.

8. Multiple images per page with a default image, and a custom in-world calendar per world.
9. JSON import and export of a world.
10. A shared, read-only D&D 5e content library (races and their traits, classes and their features), in both SRD editions, that creators can base their own custom types on.
11. A guided character builder that creates a playable character from that content, starting at level 1 and then supporting higher levels.

**Non-goals for v1:** CloudKit sync, sharing or collaboration, player and DM visibility controls, other TTRPG systems, other import/export formats (Markdown, VTT), a combat tracker.

## 2. Technical Decisions

| Area | Decision | Reason |
|---|---|---|
| UI | SwiftUI only. `NavigationSplitView` is the shell and adapts to Mac, iPad and iPhone. | One codebase, native behaviour on each platform. |
| Persistence | SwiftData, with a CloudKit-compatible schema from day one. | CloudKit can be enabled later with no migration pain. |
| Concurrency | async/await and `@Observable`. No Combine. | Project guideline. |
| Tests | Swift Testing for unit tests, XCUIAutomation for UI tests. | Project guideline. |
| Targets | One multiplatform app target. Minimum OS is 27 on iOS, iPadOS and macOS. | Gives `TextEditor` with `AttributedString`, drag-to-reorder (`reorderable()`) and current SwiftUI APIs. |

**CloudKit-compatible schema rules.** These apply to every model from the start:
- No `@Attribute(.unique)`.
- Every property has a default or is optional.
- All relationships are optional, with explicit inverses.
- Large blobs (map images) use `@Attribute(.externalStorage)`.
- Enums are stored as raw-value strings.

Later, enabling CloudKit means adding the iCloud capability and a `ModelConfiguration(cloudKitDatabase:)`. The schema needs no changes.

## 3. Domain Model

```
World                     a top-level container (e.g. "Faerûn", "My Homebrew"). A creator can have many.
 ├─ system: RuleSystemID  (.none, .dnd5e, ...), one per world
 ├─ Campaign[]            (a World can host several campaigns)
 ├─ Page[]                (all content)
 ├─ WorldMap[]
 └─ CalendarDefinition    (custom in-world calendar, see below)

CalendarDefinition
 ├─ hoursPerDay: Int                (e.g. 24, but editable)
 ├─ months: [(name, dayCount)]      (any number of months; each month has its own name and
 │                                   editable day count)
 ├─ weekdays: [String]              (optional)
 └─ eras: [(name, suffix)]          (optional, e.g. "Dale Reckoning" / "DR")
                                    Years are fixed length (no leap rules in v1).

Calendar creation flow: choose hours per day, number of months, and a default days per month,
then edit each month's name and day count individually. Days per year is the sum of the months.
Editing a calendar that already has dated events keeps stored dates valid (see below) and warns
if a change would push an existing date out of range.

InWorldDate               stored as year, month index, day, hour (and optional minute), plus era.
                          Sortable via a computed absolute hour number from the world's calendar.
                          Formatting is by calendar.

Page                      one entity for all page types, discriminated by `kind`
 ├─ id, title, summary, kind
 ├─ characterRole: .playable | .nonPlayable   (only for kind == .character; monsters are
 │                  non-playable characters, with the "monster" distinction coming from tags or
 │                  a creature-type attribute for now)
 ├─ images: [PageImage]             (many; exactly one flagged as default)
 ├─ body: AttributedString          (rich text with @mention runs)
 ├─ attributes: [String: AttributeValue]   (Codable, key-addressed)
 ├─ parent: Page?                   (hierarchy; used mainly for Places)
 ├─ tags: [String]
 └─ outgoing: [PageLink], incoming: [PageLink]

PageImage                 page, image data (externalStorage), caption, sortOrder, isDefault
                          Setting a new default clears the previous one. Deleting the default
                          promotes the next image. Thumbnails are generated for lists.

PageLink                  source Page, target Page, role (e.g. "participant", "location", "member")
                          Rebuilt from @mentions and from structured fields.

Event (data on Page.kind == .event)
 ├─ origin: .backstory | .campaign(Campaign)
 ├─ when: InWorldDate (sortable), optional end date
 ├─ location: Page?  (a Place)
 └─ participants: [PageLink role=participant]

WorldMap
 ├─ image (externalStorage), name
 ├─ place: Page?     (the place this map depicts, enabling nested maps)
 └─ (places appear on a map from their own positions)
```

**Why one `Page` model rather than six.** Linking, search, `@` mentions, hierarchy and CloudKit all work against a single type. Per-kind behaviour comes from `PageKind` plus the attribute schema. A view for a particular kind can still use typed accessors.

**Where `AttributedString` fits.** It is `Codable`. Mentions are stored as a custom `AttributeScope` attribute holding the target page ID. Renaming a page therefore never breaks links, because the display text refreshes from the ID.

## 4. Rule Systems and Attributes (data-driven)

```swift
struct AttributeDefinition: Identifiable {
    let key: String              // stable, e.g. "dnd5e.armorClass"
    let label: String
    let type: AttributeType      // .text, .number, .bool, .choice([..]), .dice, .page(kind), .list
    let appliesTo: Set<PageKind>
    let group: String            // section heading in the editor
}

protocol RuleSystem {
    var id: RuleSystemID { get }
    var name: String { get }
    var attributes: [AttributeDefinition] { get }
}
```

- A **core** set of attributes always applies to each kind (for example a Place's population or an Item's rarity-neutral description).
- `DnD5eSystem` adds attributes such as AC, HP, CR, ability scores, alignment, size, creature type, item rarity and attunement.
- The editor builds its forms from definitions, so adding a system means adding a file and no new UI.
- Values are stored by stable key. Switching or removing a system never deletes data. Unused attributes are hidden and kept.
- Until the D&D content milestone, the app ships attribute definitions only, with no rules text. Bundled content (section 5.6) is limited to openly licensed SRD material.
- **Built so far:** the `RuleSystem` protocol, the `RuleSystems` registry, `NoRuleSystem` and `DnD5eSystem`. A system can override a core attribute by reusing its key (D&D turns Creature Type, Item Type and a race's Size into pickers). The field types are text, number, bool, ability score (shown with its modifier), choice and page reference.

## 5. Features

### 5.1 Pages and editing
- A sidebar of kinds, a list per kind, and a detail editor.
- The editor has a header (title, summary, kind badge), grouped attribute sections, and a rich-text body.
- Typing `@` opens a search popover. Selecting a result inserts a mention run and creates or updates a `PageLink`.
- A **Backlinks** section lists everything that references this page.

### 5.1a World home page
- Each world has a **Home** entry at the top of its sidebar, selected when the world opens. Its page holds the world's name, a free-text summary, the rule system picker, and the world's own images (several, with a default, same as pages).
- Export and Delete are on the home page, and are the only places to do them. The worlds list is for opening, creating and importing, with no context menu or swipe actions.
- The window is two columns, sidebar and detail, so the home page uses the whole width beside the sidebar. For a page kind, the detail area holds the page list and the editor side by side (a split view on the Mac, a nested split view on iPad and iPhone). SwiftUI can't hide only the middle column of a three-column split, which is why the structure changed.
- Deleting a world leaves its screens first and deletes afterwards, so nothing is ever showing a deleted world.
- Images are shared code: pages and worlds both conform to `ImageOwner`, which holds the default-image, ordering and removal rules. World images are exported and imported with the world (an optional field, so older files still read).

### 5.1b Mentions and backlinks (as built, milestone 5)
- **Storage:** a mention is a standard link run in the notes pointing at `encounter://page/<page id>`. A custom text attribute was ruled out because it doesn't survive being saved or exported with the default coders. Tests check that links survive SwiftData and the JSON coder.
- **Typing:** `@` at the start of the text or after whitespace or `(` opens suggestions for pages in the same world. The query may contain spaces and stops at a line break or after 40 characters, so email addresses and stray `@`s don't trigger it. Choosing a page replaces `@query` with a mention and a trailing unlinked space, and puts the cursor after it. (SwiftUI otherwise leaves the inserted text selected, so the next key would replace the mention.) A **Mention Page…** button does the same for touch devices.
- **Links:** `MentionSync` keeps one `PageLink` with the role "mention" per distinct page mentioned. Mention links are derived from the text, so they are not exported, and import rebuilds them. Other roles are never touched.
- **Maintenance:** renaming a page updates the text of mentions of it (a blank title is ignored). Deleting a page turns mentions of it into plain text first.
- **Import:** mention URLs are remapped to the new page IDs, and a mention of a page that isn't in the file becomes plain text.
- **Navigation:** `WorldNavigation` holds the sidebar selection and open page, shared through the environment, so a mention or a Referenced By row can open a page of any kind.
- **Referenced By:** lists mentions and structured links (race, location, participant and so on), each described from the target's side ("Has this race", "Happened here").
- **Mentions as blocks:** the editor treats a link as ordinary text, so `Mention.normalize` corrects the notes after every edit. Deleting any part of a mention deletes all of it, text typed against a mention loses the link, and text typed inside one turns it into plain text. A mention whose text has gone stale is left alone unless it is edited.
- **Clicking a mention:** `TextEditor` hands link clicks to the system, not to the app, which showed "no application set to open the URL". So the app registers the `encounter://` scheme in `Info.plist`, receives the URL with `onOpenURL`, and `LinkRouter` opens the page in the world that is showing. `handlesExternalEvents` keeps the existing window from being duplicated. With several windows open, the world shown last receives links. macOS learns a new URL scheme at launch, and may send links to an older build of the app if several exist.
- **Known limit:** the suggestion list appears under the notes, not at the cursor, because the editor doesn't expose the cursor position.

### 5.2 Place hierarchy
- Places have a `parent`, with a place type (region, settlement, building, wilderness, point of interest and so on).
- **Root place:** every world has a root place at the top of its hierarchy, named after the world (`World.rootPlaceID`). New worlds get one when they are created, and worlds from before get one at launch, along with their parentless places and world map. Importing an older file adds one too. Every other place is inside it, so there is no "nowhere": a place with no outline around it sits directly in the root place. The root place can't be deleted or moved, and renaming the world renames it, unless it has been given a name of its own. Its map is the world map.
- **Outline and breadcrumbs (8a, built):** the Places list is an outline that opens down to the selected place. A place page shows breadcrumbs (each opens that place), a **Located In** picker, the places inside it and **Add Place Here**. Cycles are prevented: the picker leaves out the place itself and what is inside it. Deleting a place moves its contents up a level.
- **World coordinates (8b, built):** places get real positions on a flat plane of metres, like the UK National Grid: **eastings** (x, east) and **northings** (y, north) from a south-west origin, both non-negative. Users never see raw numbers. A place's `geometry` is a point (a tavern) or a polygon footprint (a settlement or region). It is stored on the page as encoded JSON, because SwiftData lost a polygon's corners when it stored the enum directly (a test caught this). Maps (milestone 11) will set positions, by drawing polygons and dropping pins on a map calibrated in metres. Until then they are set in code and tests only.
- **Spatial logic:** a pure `PlaceGeometry` calculator: validity (on the plane, a polygon needs three corners, an area and no self-crossing), area, centre, distance, point in polygon (edges count as inside) and polygon in polygon (smaller, all inside, no edge crossing out, so concave outlines work).
- **Automatic parents:** `setGeometry` refreshes the world. A place with a position and no parent chosen by the creator gets the smallest place around it as its parent. `parentSource` records who chose a parent: `automatic` (may be recalculated) or `manual` (never replaced, and choosing "Nowhere" counts as a choice). A parent with no recorded source is treated as manual. Removing a position, or the outline around it, removes an automatic parent.
- **Export and import:** `geometry` and `parentSource` are optional fields on a page record, so the format version stays 1 and older files still import. An invalid shape in a file is dropped.

### 5.3 Maps
- Import an image with `PhotosPicker` or `fileImporter`.
- **Shown with MapKit:** the map image is cut into Web Mercator tiles on demand (`MapTileSource`, an `MKTileOverlay`) that replace the base map, so even huge images zoom smoothly. The world's plane of metres is treated as the Mercator plane (`WebMercator`), which is almost true to scale near the equator. A map view wraps `MKMapView` for both macOS and iOS (`MapKitCanvas`). It gives zooming, panning, annotation clustering, polygons and a scale of its own. MapKit's "Legal" link and zoom buttons stay on screen, and rotation and tilt are off.
- Tap to add a pin, then pick or create a Place. Pins are stored in normalised coordinates, so image resolution doesn't matter.
- A place can have its own map, so a pin can drill down (region map to town map).
- Maps are kept at full size, with no limit on their pixel size, so calibration and detail aren't lost. Other images are still reduced to 4096.

- **Maps belong to places (milestone 11):** a map is a map of a place. The map of the root place is the **world map**. A map of any other place is a **settlement map** or a **scene map** (a building or battle scene on a grid of 5 ft squares). All are calibrated into the same flat plane of metres, so a position on any map means the same place in the world. A settlement is just a point on the world map. Its own map is a much smaller map in the same plane, centred on that point.
- **Reaching maps:** there is no list of maps. **World Map** sits below Home in the sidebar and opens the world map, or shows an empty state with Add Map if there isn't one. Other maps open from a pin's popover on a map, or from the **Maps** section of their place's page, which is also where a map is added (from a file, from Photos, or by dropping an image). Each map shows a trail of the places above it, each opening its own map, to go back up. The world has one map, and other places can have several, such as a floor each.
- **Calibration:** every map stores one calibration: where the image's top left corner is in the plane, metres per pixel, and a turn. How you give it depends on the type. A **world map**: mark two points and type the distance between them. The app works out the scale and puts the map north up with its bottom left corner at the plane's origin (0, 0), so every position on it is non-negative. No coordinates are typed. A **settlement map** (11b): mark two points and type the distance, and the map is centred on its settlement. A **scene map** (11b): enter the size in squares (columns by rows) and the square size (5 ft, 1.524 m), centred on its place. Two-point marking is the first method, and a more interactive one can replace it later without changing what is stored.
- **Distances:** always stored in metres. The unit shown and typed in depends on the map type (`DistanceUnit.forCalibrating`, where a setting would go later): miles for a world map, yards for a settlement map, and feet and squares for a scene map. Kilometres and metres are also supported by `DistanceUnit`.
- **One world map:** a second world map would also sit at the origin, so only one can line up. Placing further maps on a place (as settlement maps do) is the way to cover other areas for now.
- **A map must be calibrated first:** nothing goes on an uncalibrated map. Places are meant to be added by right-clicking or long-pressing on the map, so they always have a position. A settlement or scene map needs its place to have a position already. A place put on a settlement's map is made a child of that settlement.
- **Pins are derived:** a pin points at a place and is drawn from `place.geometry` through the map's calibration. A place appears on every map that covers it, and nesting between maps comes from their areas. The old `MapPin` model is removed. Older files that list pins still import, and the pins are ignored.
- **Map types in the app (11b):** a map that isn't the world map is a settlement map or a scene map, which can be changed, and changing it drops the calibration. A settlement or scene map is calibrated once its place has a position. A settlement map uses two points and a distance. A scene map takes the squares across and down and the square size in feet (5 by default), and shows a grid you can switch off. If the grid's shape disagrees with the image's by more than 5%, the panel warns but still allows it.
- **Putting places on a map (11b):** on a calibrated map, right-click on a Mac, or press and hold on a touch screen, and choose a new place (name and type) or an existing place that has no position. That sets the place's position, so automatic parents follow. A spot that would have a negative position is refused with a message. Pins show the place's icon and name. Tapping one shows Open Place, Open Map for any other map of that place, and Remove From Maps. Dragging a pin moves the place. A place page lists the maps that show it.
- **Outlines (11c):** on a selected place, Draw Outline lets you click its corners, with Undo, Cancel and Finish. It must have three corners and not cross itself or reach off the edge of the world. Finishing it sets the place's outline, and 8b's automatic parents then put the places inside it inside that place. A place with an outline is drawn at the middle of it, can't be dragged (it is redrawn instead), and can be turned back into a point. Clicking inside an outline selects its place, and the smallest outline wins.
- **Steps:** 11a: import, view, zoom, and world map calibration. 11b: adding places on the map, the map types and their calibration. 11c: MapKit, outlines and clustering.
- **Limit:** a world has one plane. Building floors, dungeon levels and other planes would overlap on it, and will need their own plane (a "space" a place belongs to) or a height value later. The geometry maths wouldn't change.

### 5.3a Calendars (milestone 10)
- **Editor:** the world's home page shows the calendar and opens a sheet to edit it: months (name, days, add, delete, reorder), hours in a day, days of the week, and starting presets (twelve months of 30 days, and Gregorian). A "Try a Date" row shows how a date reads.
- **Dates:** `InWorldDateField` picks a year, a month by name, a day that exists in that month and an hour if the day has more than one. Changing the month keeps the day if it fits (`clamped`). `format` reads a date as "14 Frost 1203", or "Moonday 14 Frost 1203, hour 6".
- **Years before 0:** allowed. They order before year 0, and weekdays count back from it.
- **Weekdays:** year 0, month 1, day 1 is the first weekday listed. A different starting weekday isn't supported yet.
- **Editing a calendar under existing dates:** dates are never changed. The editor warns how many dates in the world no longer fit.

### 5.4 Events, timelines and movement
- Events carry an in-world date, a location and participants.
- **Editing (12a, built):** an event page has When, Where and Who Took Part sections. **Part Of** is Backstory or Campaign, and backstory belongs to no campaign. Putting an event in a campaign makes it a campaign event, and taking it out makes it backstory. **Dates** use the world's calendar: a start, and optionally an end. An event with no start has no end. An end before the start is moved up to the start, and moving the start past the end moves the end with it. **Location** is any place page, whether or not it is on a map. **Participants** are characters and organisations, added from a searchable list, each once.
- **Campaigns (12a, built):** a **Campaigns** item in the sidebar, below World Map. It lists campaigns with their event counts, edits a name and summary, lists the campaign's events by date, and adds a new event to it. Deleting a campaign keeps its events and makes them backstory.
- **Timeline (12b, built):** a **Timeline** item in the sidebar, below World Map. It lists the world's events by start date, grouped by year with a pinned header, and undated events last under "No Date". An event whose date the calendar no longer holds counts as undated. Events at the same time are ordered by title. Each row shows the date (or date range), the title, and the place, participants (three, then "and n more") and campaign. Filters narrow it, and all that are set must match: backstory or a campaign, a character, an organisation, and a place, which includes everything inside that place. New Event starts out matching any filter that is set, so it doesn't vanish. The list is a scrolling stack rather than a `List`, because SwiftUI's macOS `List` crashed on this layout.
- The **character journey** is derived. For a character, take the events they participated in, order them by date, and read each event's location. That gives an ordered list of places.
- Journey display is a list and timeline first. A path overlaid on a map comes later, using pins for the places.
- Nothing is stored for movement. It is always computed from events, so it can't go stale.

### 5.5 Search
- **Plain text of notes:** `Page.bodyText` holds the notes as plain text (mentions as their titles), so notes can be searched in the database. It is derived from `body`, refreshed by `updateSearchText()` wherever the notes change (the editor, mention renames and deletes, import, the builder, Create Custom Version), and filled in at launch for older notes. It isn't exported, and import rebuilds it.
- **Search field:** the world's `searchable` field. While it has text, the results replace the detail area. Choosing a result opens it and clears the search, as does choosing anything in the sidebar. A picker narrows the search to one kind of page, or the library.
- **Matching:** a result must contain every word typed, each in the title, tags, summary or notes. Matching ignores case and accents and finds a word anywhere in a word. The database narrows by the longest word, and the rest is checked in memory.
- **Ranking:** the title being the search, then starting with it, then a word starting with it, then containing it, then the words spread through the title, then tags, summary and notes. Each result shows what kind it is and, if the title didn't match, the matching text.
- **Library:** entries of the world's edition are searched by name and summary alongside pages, not by their full text.
- **Not done:** the `@` mention picker still matches titles with its own query and order. Core Spotlight indexing is still later.

### 5.4a Navigation on iOS and macOS
- **macOS** shows the world's menu beside the screen it chose (`NavigationSplitView`), and each list beside its editor (`HSplitView`).
- **iPad at regular width** (and an iPad window wide enough) is laid out like the Mac: the menu beside the screen, and each list beside its editor (a fixed-width list and a divider, since `HSplitView` is macOS only). In a narrow window the menu slides over the screen and closes when a row is chosen.
- **iPhone and narrow iPad windows** (compact width) use a single navigation stack, the one the world list already has. The world's menu is a list of buttons that push the chosen screen, and a list pushes its editor on top of it. Something opened from elsewhere (a link, a pin, a search result) pushes its screen too. A split view inside that stack doesn't navigate when collapsed, so it isn't used there.
- Screens pushed this way don't inherit what was set inside the world screen, so `WorldNavigation` is passed to each one explicitly.

### 5.6 D&D 5e content library

Races or species with their traits, and classes with their features, shipped with the app as a shared library.

- **Shared and read-only:** the library is bundled with the app and is not stored in any world. Every world sees the same entries, so a content update reaches all worlds, and CloudKit never has to sync it. Library entries can't be edited.
- **Custom versions:** from any library entry, **Create Custom Version** makes an ordinary, editable page in the current world (a homebrew variant). The copy remembers which library entry it came from (`basedOnKey`).
- **Editions:** the open SRD exists as 5.1 (2014 rules) and 5.2 (2024 rules), and both are bundled. Each **world** chooses its edition (a setting on the world, next to its rule system), and the library shows that edition's content. In 5.2 the interface says "Species" instead of "Race".
- **Content format:** bundled JSON content packs, one per edition, with stable keys such as `srd51.race.elf`. Packs use the same record format as world export (section 7), so there is one parser.
- **Library entries:** a name, summary, attributes (size, speed, hit die and so on) and structured **entries** (see below), plus the source and attribution.
- **Races and species:** size, speed, darkvision, languages and a list of traits. Subraces refer to their parent.
- **Classes:** a new page kind, **Class**, with hit die, primary ability, saving throw proficiencies, armor and weapon proficiencies, spellcasting ability, and features by level. Subclasses refer to their class.
- **More kinds (milestones 7a to 7d):** skills, backgrounds, feats, equipment and spells, in both editions. The SRDs hold one background in 5.1 and four in 5.2.1, so most backgrounds are creators' own pages. They are read the same way as library ones.
- **Structured entries:** traits and class features are lists of entries (name, description and, for classes, level). `AttributeValue` gains an entries case, and the page editor gains a list editor for it.
- **Browsing:** a **Library** section in the sidebar lists library entries read-only, with the Create Custom Version button. Library entries also appear in search and in the pickers below.
- **Referencing library content:** a character's race and class can each be a world page or a library entry. Pickers show both, grouped as "This World" and "Library". A world page is stored as a `PageLink`. A library entry is stored by key, in an attribute such as `core.raceLibraryKey`. Exactly one of the two is set.
- **Missing keys:** a reference to a key the installed library doesn't contain (a newer export opened in an older app) shows as "Unavailable library entry" and loses nothing.
- **Export and import:** a world export stores library references as keys, not as content, so exports stay small. Custom versions export as ordinary pages.
- **Class category visibility:** the Classes category shows in the sidebar when the world's rule system has classes, or when the world already contains class pages. So worlds on "None" don't see an empty Classes category, and switching systems never hides existing pages.
- **Characters:** a character has a class reference and a Class Level, next to its race. Playable and non-playable characters still share one form.
- **Licensing:** only openly licensed SRD content is bundled, with the required attribution shown in the app (an About screen) and stored inside each pack. Anything outside the SRD isn't shipped. Creators can write their own pages and custom versions.

**Licensing, verified against the official PDFs.** Both SRDs are under CC-BY-4.0, and each requires its own attribution statement in the work. These are the exact statements on page 1 of each document. Wizards asks that no other attribution to Wizards be added, and CC-BY-4.0 requires saying if the material was changed.

- SRD 5.1: *This work includes material taken from the System Reference Document 5.1 ("SRD 5.1") by Wizards of the Coast LLC and available at https://dnd.wizards.com/resources/systems-reference-document. The SRD 5.1 is licensed under the Creative Commons Attribution 4.0 International License available at https://creativecommons.org/licenses/by/4.0/legalcode.*
- SRD 5.2.1: *This work includes material from the System Reference Document 5.2.1 ("SRD 5.2.1") by Wizards of the Coast LLC, available at https://www.dndbeyond.com/srd. The SRD 5.2.1 is licensed under the Creative Commons Attribution 4.0 International License, available at https://creativecommons.org/licenses/by/4.0/legalcode.*

- The app shows the matching statement on every library screen and on an About screen, and each pack carries it. A note says the text was reformatted for display and that its wording is unchanged.

**Sourcing the content.** Rules text is taken from the official PDFs by a converter tool, never typed from memory, so the wording is exact. The tool lives in the repository (like the sample world generator), strips page furniture and whitespace artefacts, and writes the packs. Each pack is checked: every expected race or class is present, class features carry the right levels (cross-checked against each class's progression table), and no text is cut off.

**Content pack format (draft).** One JSON file per edition, bundled in the app:

```json
{
  "formatVersion": 1,
  "id": "srd51",
  "name": "SRD 5.1",
  "edition": "5.1 (2014 rules)",
  "raceTerm": "Race",
  "attribution": "<the statement above>",
  "entries": [
    {
      "key": "srd51.race.elf",
      "kind": "race",
      "name": "Elf",
      "parent": null,
      "summary": "Short description.",
      "attributes": { "core.raceSize": "Medium", "dnd5e.speed": "30 ft.", "dnd5e.darkvision": "60 ft." },
      "entries": [ { "name": "Keen Senses", "level": null, "text": "You have proficiency in the Perception skill." } ]
    },
    {
      "key": "srd51.class.fighter",
      "kind": "class",
      "name": "Fighter",
      "attributes": { "dnd5e.hitDie": "d10", "dnd5e.savingThrows": ["Strength", "Constitution"] },
      "entries": [ { "name": "Second Wind", "level": 1, "text": "…" } ]
    },
    { "key": "srd51.subclass.champion", "kind": "subclass", "name": "Champion", "parent": "srd51.class.fighter", "entries": [ … ] }
  ]
}
```

- Keys are permanent. They are never reused or renamed, because worlds refer to library entries by key.
- `kind` is `race` (species in 5.2.1), `class` or `subclass`. A subclass names its class in `parent`, and a subrace names its race.
- `attributes` use the same keys as page attributes, so a custom version is a plain copy.
- `entries` are the structured traits and features: a name, an optional level and the text.

### 5.7 Character builder

A guided flow that produces a playable character page.

1. **Name and concept:** name, alignment, optional portrait.
2. **Race or species:** pick from the library or the world's own pages, and from subraces where there are any. Traits and ability bonuses are shown.
3. **Class:** pick from the library or the world's own pages, with a summary of the features for the chosen level.
4. **Ability scores:** standard array, point buy, or manual entry. Rolling in the app can come later. Racial bonuses are applied and the modifiers shown.
5. **Review:** a summary with derived values such as proficiency bonus, hit points and armor class (10 plus Dexterity modifier, until equipment exists).
6. **Create:** makes a playable character page with its race and class references and all attributes filled in. The creator can then edit it like any other page.

- Derivations live in plain Swift types (a `CharacterDraft` plus calculators) so they're unit-tested without UI.
- The builder reads the library and the world's own pages together, so homebrew races and classes work the same as bundled ones.
- **Level 1 first:** milestone 7e builds level 1, including **skills, equipment, spells and backgrounds**, so those are added to the library first (milestones 7a to 7d).
- **Editions differ:** in 5.1, ability score bonuses, languages and some proficiencies come from the race. In 5.2.1 the ability score bonuses, two skills, a tool and an origin feat come from the background, and species have none.
- **Few backgrounds in the SRD:** the 5.1 SRD has one background (Acolyte) and 5.2.1 has four. The builder treats library and world backgrounds alike, so creators add their own as pages, starting from Create Custom Version.
- **Higher levels soon after:** a later milestone (13, after events and timelines) adds levelling up to a character page: choosing the new level, applying hit points, proficiency bonus changes and the class features gained, with subclass choice where the class requires it.

### 5.8 Character sheet (milestone 14)

A read-and-play view of a character, laid out like a D&D sheet. It sits on the character's page as a **Sheet** view beside the page's own fields, and what you edit on the sheet goes straight back to the character page, so there is one set of data.

- **Header:** name, race or species, class and level, background, alignment.
- **Abilities and skills:** the six ability scores with modifiers, saving throws, and the 18 skills, with proficiency marked and the bonuses worked out.
- **Combat:** hit points (current, maximum and temporary), hit dice, armor class, initiative, speed, proficiency bonus, and attacks from the equipped weapons.
- **Features and spells:** class, race and background features by level, and the spell list with slots and the spells prepared or known.
- **Equipment and notes:** equipment and money, languages and proficiencies, and the character's own notes.
- **Play:** current hit points and spell slots can be changed from the sheet, with the maximums coming from the character's level.
- **Actions:** every weapon, spell, ability check, saving throw and skill on the sheet can be tapped to open a card that says exactly what to roll and what to add. A longsword reads "Attack: d20 + 5 (Strength +3, proficiency +2). Damage: 1d8 + 3 slashing". A fireball reads "Each creature in the area makes a Dexterity saving throw against DC 15. Damage: 8d6 fire, half on a save". Attack spells show the spell attack bonus, and weapons use Strength or Dexterity as their properties allow (finesse, ranged, thrown).
- **Rolling in the app (optional):** a setting turns on Roll buttons on those cards. A roll shows each die, the modifier and the total, with advantage and disadvantage, a critical hit on a natural 20 that doubles the damage dice, and a short log of recent rolls on the sheet. With the setting off the cards only say what to roll, for players using real dice. The dice live in a plain Swift roller with a replaceable source of randomness, so they are unit-tested.
- **Spell slots:** casting a spell from its card spends a slot. The card offers the slots the character has left, from the spell's level up, and says what changes when cast at a higher level. Cantrips spend nothing, and a ritual can be cast without a slot. Slots are shown as dots to tap by hand too. A warlock's pact slots come back on a short rest, all other slots on a long rest.
- Derived values come from the same plain Swift calculators the builder and levelling use, so they are unit-tested without UI.
- **After levelling:** the sheet comes after milestone 13 so it is built once on full level 1 to 20 data rather than reworked. A printable PDF is not planned yet, and can be added on top of the sheet later.

### 5.7a Levelling up (milestone 13)

- **Data:** each class entry in a pack carries its table as plain text attributes (`dnd5e.asiLevels`, `dnd5e.cantripsKnownByLevel`, `dnd5e.spellsKnownByLevel` or `dnd5e.preparedSpellsByLevel`, `dnd5e.spellSlotsByLevel`, `dnd5e.pactSlotsByLevel`, `dnd5e.invocationsKnownByLevel`), so a custom class made from a library class levels the same way and its table can be edited. A class made from scratch has no table and can't be levelled.
- **Reading the tables:** the SRD PDFs scatter a table row's numbers away from its label, so the converter reads each table as twenty rows of numbers in order, and the checks fail the run if a column ever falls as the level rises or the level 20 slots aren't the rules' ones.
- **Rules:** `ClassProgression` and `LevelRules` are plain Swift, tested without UI. A level gives the average roll (half the die rounded up) or a roll, plus the Constitution modifier, at least 1. A Constitution increase also raises the hit points of every earlier level. An improvement is 2 points in one ability or 1 in two, never above 20, or a feat (general and fighting style feats, and epic boons from level 19 in the 2024 rules).
- **Spells:** a caster learns the difference in the table (known in 2014, prepared in 2024) from its class list, up to the highest level it has slots for. A wizard adds two spells to the spellbook with each level. 2014 clerics, druids and paladins prepare from their whole list each day, so they choose nothing.
- **Not in this milestone:** multiclassing, swapping a known spell for another, choosing eldritch invocations, and recalculating armor class or other values the creator may have changed by hand.

### 5.9 Map generators (milestone 15)

Generate maps instead of importing them, for the three kinds of map the app has. **A generated map is vectors, not a picture.** Everything the generator makes is a place, with a shape in the world's plane of metres, and the map is drawn from those places.

- **What is made:**
  - **Areas** are polygons: regions, seas and lakes, forests, mountain ranges, districts and so on. Each is a place with an outline.
  - **Settlements** are places: a point on a world map, or an outline when zoomed in.
  - **Buildings** are polygons, and each is attached to a sub-place of its settlement (a smithy, a tavern, a house), so it has a page, a parent and everything else a place has.
  - **Roads and rivers** are polylines. A named road or river is a place too, with a line for its shape.
  - **Scene maps** make rooms as polygons and walls and corridors as lines, on the grid of 5-foot squares. Doors, stairs and features are places.
- **No image:** a generated map has no picture to cut into tiles. MapKit draws its places as overlays, each styled by its place type (water, forest, road, building and so on), and the same map stays sharp at any zoom. A plain background replaces the tiles. Imported pictures work as they do now, and a map can have both: a picture below, with places drawn over it.
- **Places are the map:** since the map is its places, moving a corner of a settlement, redrawing a lake or deleting a road is editing the map. Pins, outlines, journeys, the hierarchy and "only the higher-level place is shown" work on generated maps unchanged: a building shows on its settlement's map and not on the world's.
- **A new shape:** the place shapes the app has today are a point and a polygon. A line (a polyline of points, with the same metre coordinates and spatial maths) is added for roads and rivers.
- **Detail by zoom:** what is drawn depends on the zoom, so a world map shows regions, rivers and settlements, and a settlement map shows streets and buildings. Each place type has a level it appears at.
- **From a seed:** the same seed and options always give the same map, so a map can be regenerated, or tweaked (a different sea level, more rivers) and compared. The seed and options are kept with the map, and regenerating asks before it replaces the places it made, leaving alone any place the creator has edited or added.
- **Made here, not by a model:** the generators are algorithms in plain Swift with a seeded random source, so they are unit-tested, with no network and no cost. A built-in style gives each place type its colours and line weights, and a map can be exported as an image or as vectors.
- **Open choices:** which styles to ship, whether generated places get names from a name list, and how a settlement's street layout is chosen (planned grid, organic, or radial around a centre).
- **Order of work:**
  - **15a, the foundation (built):** the line shape for places and the spatial maths for it; maps with no picture (added as a **Blank Vector Map**, calibrated from the start, kept in the world file); styles by place type (water, forest, mountains, settlement, building, river, road and so on) and the drawing of areas and lines over a plain background, in order from the bottom up; drawing and redrawing a line by hand; picking a road or river by clicking near it. The generators below make places for this to draw, so it has to work by hand first.
  - **15b, settlements (built):** a **Generate Settlement…** button on any place that is on the world map. It asks for a size (hamlet, village, town, city), the street layout (planned grid, radial, organic), whether it has a wall and a river, and a seed, and shows the result before making it. It makes a vector map centred on the place, and a place for each quarter, street, wall, river and building, all as parts of the settlement (so the settlement's own map shows them all). Buildings get names and roles (an inn, a smithy, a chapel, a hall, shops, houses numbered along their street). If the place has an outline drawn on the level above, the settlement fills that outline: the outline is its edge (and its wall, if it has one), the size comes from the outline rather than the choice, and the map is made big enough to hold it. Making it again replaces the places it made, except any that have been renamed, moved, linked or written about.
  - **15b2, settlements made from wards (built):** the first settlement generator (streets laid out on a grid or spokes, buildings placed along them) looks artificial: the radial and organic layouts are alike, every spoke meets at one point, and a big planned grid draws as a solid block. It is replaced by a generator that works the way real towns grow. It is written from the general techniques (Voronoi cells, shortest paths, polygon bisection), described in [Watabou's Medieval Fantasy City Generator](https://watabou.itch.io/medieval-fantasy-city-generator/devlog/22717/future-plans-for-mfcg) and in [Chen et al., Interactive Procedural Street Modeling](https://www.sci.utah.edu/~chengu/street_sig08/street_project.htm), and not from the GPL-3.0 source of either, which is not read or copied.
  - **15b3, blocks and the river (built):** the organic layout is made in three steps: the main roads (gate to square, and a few more between them) are found along Voronoi cell edges, each road is smoothed into a curve through its own corners (a centripetal Catmull-Rom spline, so junctions still meet), and the wall, the river, the roads and the square are overlaid and cut into blocks (found as the faces of the planar map of those lines), with big blocks cut again, across their long way and a little off square, into wards and side streets. The river is a break in every layout: planned and radial wards are cut where the river runs through them, so a ward is on one side or the other; main roads cross it only at a few bridges (crossing is dear, and roads share one where they can), and side streets stop at the bank. If the blocks don't come out right the organic layout falls back to the cells of the diagram.
  - **15b4, quarters and venues, not buildings (built):** a settlement no longer gets a place for every house (hundreds of pins made the map unusable). It makes the streets and roads (named), the wall and gatehouses, the river, the square, the quarters, and the landmarks the user picked. A quarter (or the old town) is made only if it is big enough to matter: at least about a ward and a half, and 5,000 square metres. Two switches, **Inns and Taverns** and **Merchants**, each add a number to suit the size (hamlet 1 and 1, village 2 and 4, town 4 and 10, city 8 and 22), spread round the settlement: an inn by the square and the gates and then spread out, merchants by the square and in the merchant and craft quarters and then spread out. Everything else is for the people running the game to add.
  - **Naming: root languages (19f, built (steps 1 to 4)).** The naming styles built first (English, Italian, German, Norse, Welsh) are a start, but they mix three things that must be separate. The specification, agreed on 3 November 2026:
    - **Root languages supply proper names; the user's language supplies plain words.** A name is a *proper name* in a root language plus, where the place type needs one, a *plain term* in the user's language. Plain terms are the nouns that say what a thing is: Street, Road, Lane, Gate, Bakery, Tannery, Chapel, Cathedral, River, Manor, Keep, Kingdom, Forest, and the joining words ("of", "the", possessive 's). Everything else is part of the proper name and comes from the root language, including words that mean something in English such as Mill, Oak, Golden, Stag, Iron, Old and Mercy. So "Mill Street" is a root-language word for mill with the plain term Street, and "The Golden Stag" is a root-language name. "North Gate Road": "North Gate" is the proper name (root language) and Road the plain term; the gate itself is "North Gate" with Gate the plain term.
    - **A realm has one or more root languages with weights** (for example Celtic 60, Slavic 40). A place name is usually wholly in one language, picked by weight, and sometimes a blend of two (a Celtic start with a Slavic ending), as real places are. How often a blend happens is a setting (per world, with a default).
    - **Settlements inherit from their realm.** A settlement inside a realm on the world map uses that realm's languages, shown in the Generate Settlement sheet with the option to change them; one outside any realm uses what is chosen in the sheet.
    - **Language data is a standard structure** (one file format, `Content/naming.json`, to be reworked): each root language gives, for a fixed list of *concepts*, the word in that language (mill, bridge, oak, golden, stag, iron, mercy, and so on, grouped by what they are used to name: street themes, inn adjectives and animals, saints and virtues, trades named for a person), plus lists of personal names, place-name starts and ends, realm names, the order its two-word names take (adjective first or noun first), and optionally whole phrases it wants used as they are. A language may lack a concept, which is skipped. Names carry no articles or agreement: the root language gives bare words, which is also what makes a language easy to write.
    - **Plain terms are English in the code, with keys, ready to translate.** They live in one table (key and English text, such as `term.street` / "Street", `term.bakery` / "Bakery") and are shown through the app's localisation, so translating the app translates them. The patterns that join a name and a term (the order, "{name} Street", "Chapel of {name}", "{name}'s Bakery") are in the plain-term table too, because word order differs between languages.
    - **Custom languages later.** The format is complete and documented now, a language is just a file, and the app finds the ones it ships with; nothing in the app lets a user add one yet.
    - **Not in this step:** the AI work. After this, we explore whether Apple's on-device model (Foundation Models) could write a new root language from a description of a realm, and write realm descriptions during world generation ("inspired by eastern Europe", "dwarvish names after Tolkien"): a written report with a design and a small prototype to judge the quality, before anything ships.
    - **Steps, each ending with a check-in:** (1) the language format, the plain-term table, and the existing five written again into the new structure, with a test that English-language names for a seed are the same as before; (2) a realm's languages and weights in world generation and on the world map; (3) settlement inheritance and the sheet; (4) the blend setting. The word lists need a reader who knows each language.
    - **Step 1, built:** `Content/naming.json` is format version 2: a fixed list of concepts in groups, and six languages (English, Celtic, Slavic, Romance, Germanic, Norse), each with a word per concept, which side the describing word goes on, and lists of personal and place names. `NameTerms` holds the plain terms as localisable strings. `NameBank` builds names from a language plus those terms. The old ids italian, german and welsh still open as romance, germanic and celtic. A test checks that English names for four seeds are exactly as before. The word lists were written by me and need reading by someone who knows each language. Options still hold a single language id; realm languages with weights come in step 2. Not seen in the running app.
    - **Step 2, built (3 November 2026):** every river, made up or from the world map, now has a street along each bank, between 8 and 18 metres back from the water by the size of the settlement. The wards are cut by the river and by a line each side of it (`makeBankLines`); the edges along those lines are ordinary streets, named for the river as "Hale Quay" and "Hale Embankment" (the plain words in `NameTerms`, the river's own name taken from "River Hale"); the strip between each street and the water is marked `isBank` and gets no buildings, districts, quarters or landmarks; the short cuts across the strip are dropped unless a main road crosses there, which is the bridge. The main square is moved off the strip if it would fall on it. A bank line that would cross itself on a sharp bend, or that makes the blocks come out wrong, is left out, and the river is then as before (about one settlement in eight in the test seeds). A river settlement now names its river before its streets, so the names drawn for seeds with a river differ from before, as do their layouts. Rendered in the preview of three layouts: both banks show in all three. Not looked at closely at the size of a real map, and not seen in the sheet.
    - **Step 2, built:** world options hold languages with weights for each realm (`realmLanguages`, by realm number; a realm with none uses the Names choice). Generate World shows a Realm 1, 2, … list, each with a switch per language and a share from 1 to 100. A name is made in one language picked by weight; the realm's name and every settlement in it use that realm's languages, while the sea, forests, mountains and rivers use the Names choice. The choices are saved with the map's options. A world with no realm languages chosen gives the same names as before (tested). Blended names (two languages in one name) are step 4. Settlements opened from the map don't inherit yet (step 3). Not seen in the running app.
    - **Step 3, built:** a region the world generator makes records which realm it is (`gen.realm`), and a place's realm is the one whose area holds its position on the world map. The Generate Settlement sheet, for a place in such a realm, shows "Names from the realm (Celtic and Slavic)", on by default; switching it off shows the same language switches and shares to change them for this settlement. Outside a realm it is the single Names picker as before. Settlement options keep the languages and whether they follow the realm, and a saved settlement opened again follows the realm's current languages unless changed. Worlds made before this have no realm recorded, so their settlements fall back to the Names picker until the world is generated again. Scenes still use the single picker. Not seen in the running app.
    - **Step 4, built (changed from the spec: no user setting):** `NameBank.blendChance`, 0.25 by default (`defaultBlendChance`), is the chance that a two-part name takes its parts from two languages of the mix. It applies to settlement names (start and end) and inn names (describing word and noun, in the order of the noun's language). With one language nothing is drawn, so English names are unchanged. Nothing in the app sets it; a world or user setting can feed it later. One-word names (streets, chapels, forests) are never blended.
    - **Follow-up (3 November 2026, after the word lists were read and approved):** a realm's name is now two parts, a start and an end (`realmStart`, `realmEnd`, replacing `realmName`), like a settlement's, and in a blend the two may come from two languages. The lists of names were made longer: owners (shops, manors, landmarks) about 40 to 48 each, rivers 23 to 32, place starts 26 to 62 and ends 18 to 30, realm starts 16 to 30 and ends 12 to 16. The words by concept (streets, inns, virtues and the like) are not longer. The test that English names for a seed are as they were was removed, since this changes them on purpose, and a map generated again from its seed now gets new names.
    - **AI-assisted naming: exploration (3 November 2026).** Apple's Foundation Models framework runs a model on the device (`SystemLanguageModel`), with guided generation (`@Generable` structs and `@Guide` limits on array length) and an availability check (not eligible, Apple Intelligence off, model not ready). The on-device context is **4,096 tokens per session**, covering instructions, prompt, the generable type's schema and the reply, so a whole language does not fit in one request. There is also a larger `PrivateCloudComputeLanguageModel` (bigger context, stronger reasoning, needs an entitlement and has a per-user quota); it was not tried. A prototype is in `Generators/RootLanguageDrafter.swift` (not used by the app): 17 short sessions draft a language from a description, a separate step checks it and turns it into a `RootLanguage`, borrowing English for any group the model got wrong. Tests: the checking and assembly run anywhere; two tests call the real model only when `RUN_MODEL_TESTS` is set.
      - **What it did on this Mac** (description "Eastern European, Slavic, with long vowels and soft consonants"): a language took **68 seconds**, three realm descriptions took **11 seconds**. *Realm descriptions are good*: concrete, varied, each from a different inspiration (Celtic, Norse, Amazonian), though two sentences ran on and one stopped on a dash. *A language is not good enough*: town starts came back as first names (Svetlana, Ivan, Tomasz) instead of syllables; a list asked for 14 endings gave "ova" fourteen times; inn adjectives repeated one word ten times; the compass words were garbled; for the street and gate groups the count was wrong and English was borrowed; towns came out as "Svetlanaova". Plausible surnames and some inn nouns were fine.
      - **Findings.** (1) The count guide fixes the length of a list, not its variety, and the small model degenerates into repeats on long lists. (2) The model is weak at translating a concept list word for word, so the concept groups are the part to leave out. (3) It is slow enough (a minute) to need a progress indicator and to run in the background. (4) It is not deterministic, so a drafted language must be saved as JSON (the same format as a shipped or custom language), never regenerated from a seed. (5) It may be unavailable (older devices, Apple Intelligence off) or refuse a request, so every use must be optional with the normal path unchanged.
      - **Recommendation, in order.** First, *realm descriptions in world generation* (an optional "Describe realms" step; the descriptions are saved on the realm pages). Second, *choose languages from a description*: the model reads "inspired by eastern Europe" and returns weights over the shipped languages (Slavic 70, Germanic 30), a small, reliable output that fits the realm languages already built, and needs no new words. Third, *a new language drafted from a description*, only if wanted after those: draft just the name lists (starts, ends, family names, rivers) in several small requests of about 10 names, seeded with real examples, dropping repeats and asking again until each list is long enough, shown to the user to edit before saving, with the concept words borrowed from the closest shipped language. The private cloud model is worth trying for that third step.
    - **Choosing languages from a description (built, 3 November 2026; first of three agreed steps: 1 this, 2 many more languages, 3 realm descriptions).** Each realm in Generate World has a description box ("What is this realm like?") and a Suggest Languages button, which asks the on-device model (`LanguageChooser`) to pick up to three of the shipped languages with shares; the result fills the realm's switches and shares, which can still be changed. The model's schema is built at run time from the shipped language ids, so new languages are offered to it automatically; its answer is cleaned (unknown ids and repeats dropped, shares 1 to 100, at most three). Where the model is unavailable the button is disabled and says why, and nothing else changes. Descriptions are kept with the world options (`realmDescriptions`). On this Mac, 2 to 5 seconds a request; Viking raiders gave Norse, Welsh hill farmers Celtic, Renaissance Italy Romance 80 and Germanic 20, "Dwarvish names after Tolkien" Germanic 90 with Slavic and Norse, and "eastern Europe" Slavic 80, Germanic 70, Celtic 60 (the Celtic is a poor fit: with only six languages the model has little to choose from, which step 2 should help). Not seen in the running app.
    - **More languages (step 2 of the three, in batches).** Batch 1, built 3 November 2026: Greek, Finnic (Finnish and Estonian) and Iberian (Spanish and Portuguese), each with all 132 concept words and the same name lists as the first six. Batch 2, built 3 November 2026: Arabic, Persian and Turkic (Latin letters, no diacritics for Arabic and Persian). Batch 3, built 3 November 2026: Chinese (pinyin, no tone marks), Japanese (romaji), Korean (revised romanisation) and Indic (Sanskrit and Hindi, no diacritics). Batch 4, built 3 November 2026, completing the 16 asked for: Swahili, Yoruba (no tone marks), Amharic (romanised), Nahuatl, Quechua and Maori (no macrons). **These six are first drafts of uneven reliability**: Swahili is the most dependable; Maori, Quechua and Nahuatl have sound place and nature words but several trade and inn words are guesses (Quechua's mill is a Spanish loan); Yoruba and especially Amharic are the least certain, and Amharic in particular has words I could not verify. Each needs a reader who knows the language before release; until then they can be left out of the picker by removing them from `naming.json`. As with the first six, the word lists were written by me and need a reader who knows each language; Finnic and Greek are the most likely to need correcting (cases and word forms), and Iberian blends Spanish and Portuguese.
    - **Realm descriptions (step 3 of the three, built 3 November 2026).** Generate World has a Describe Realms button that has the on-device model write a description for each realm that has none (ones already written are kept), two sentences on the people, land and character that name the culture it draws on. They fill the description boxes, which can be edited, and Suggest Languages can then read them. When the world is generated, a realm's description becomes the summary of its place page (a realm with none keeps "A realm."); the description changes no name or position. Unavailable model: button disabled with the reason. On this Mac the three descriptions read well and ran to whole sentences, e.g. "The people of Aeloria are fierce warriors who honor their ancestors through ritual combat, inspired by Norse mythology…"; they lean on well-known cultures (Norse, Polynesian, Maya). Not seen in the running app. This completes the AI-assisted naming work asked for.
    - **Parked (3 November 2026):** native-speaker review of all the language word lists (the first six were read and approved; the later ten have not been read, Amharic, Yoruba, Quechua, Nahuatl and Maori least reliable), to be done before release. Worlds made before realm languages existed fall back to the Names picker in the settlement sheet; accepted, since a realm's languages only matter when generating new maps.
    - **Parked (3 November 2026):** a market square scene defaulting its inn and shop names to the languages of the realm it is in (as settlements do); scenes otherwise name almost nothing ("Room 1", "Door"), so the single Names picker stays.
  - **Rivers from the world map into settlements (19f, specified 3 November 2026; both steps built).** Agreed:
    - **Which river:** the river (any river place on the world map, generated or drawn) that passes within about the settlement's own radius of its middle. The settlement uses that stretch of it, keeping its direction and bends, instead of making one up. One further away is ignored. Only the nearest one: tributaries and confluences are left for later (the answer to the question about them was ambiguous, and this is the simpler reading).
    - **No override.** If the world map has a river there, the settlement has it, and the River switch in the sheet comes on by itself and says it is from the world map. Where the world map has none, the switch works as now and makes a river up.
    - **Roads along both banks, for every river** (world-map or made up): a street runs along each bank a little back from the water, blocks on the near side face the river, and bridges cross at a few places where the main roads meet it. The strip between the street and the water has no buildings.
    - **Steps, each ending with a check-in:** (1) find the river, carry its stretch into the settlement's own coordinates (kept with the settlement's options so it can be made again, and drawn in the sheet's preview), use it in place of the made-up one, the switch showing where it came from; (2) the bank streets, the facing blocks and the bridges, for any river.
    - **How:** the settlement is cut into wards along the river line; step 2 adds a line each side of it as extra cuts, makes the edges along them streets (named from the river, as "Hale Quay" or so, the plain word in the user's language), and keeps the strip between them free of buildings. Not seen in the running app until built.
    - **Step 1, built:** `World.riverNear` finds the nearest river place within the settlement's radius of its middle and returns its stretch in metres east and north of the middle (with its name), reaching past the edge of the map. `SettlementOptions` keep it (`riverPath`, `riverName`), turning `hasRiver` on; `TownMaker` uses it in place of the made-up river, cut at the edge of the map, and names the river after the world map's. `World.generateSettlement` looks it up itself, so it does not depend on the sheet. In the Generate Settlement sheet the River switch is replaced by "River from the world map: Hale" where there is one, and the preview uses it; options saved with a map river let go of it when the world map no longer has one. Tested with a river running four different ways, and the nearest, far and cut-off cases. Not seen in the running app. Bank roads are step 2.
  - **World land and coast shapes (19f, specified 3 November 2026, not built).** The first version makes land by one noise field with a fall-off, cut at a level and smoothed: coasts are lumpy but have no bays, headlands or peninsulas, small islands are filtered away or not made, Island comes out much like Continent, and any lake is filled in as land. Agreed:
    - **Land shapes become Continent, Coast, Peninsula and Archipelago.** Continent (sea all round) and Coast (sea along one side, the land running off the map) stay and get better coasts. **Island is dropped** (it came out the same as Continent); saved worlds that used it open as Continent. **Peninsula** is a variant of Coast: a big land joined to one edge of the map by a neck, with sea on three sides. **Archipelago** is many islands in the sea, from one island per realm up to many smaller ones.
    - **Coast features:** bays and gulfs (the sea cutting into the land in rounded inlets with headlands between), peninsulas and capes (long arms of land reaching into the sea), and islands off the coast. Not asked for: fjords, deltas, two continents, inland seas.
    - **Controls in Generate World:** Land (the shape), **Coastline** (Smooth, Natural, Rugged: how much the coast bays and juts) and **Islands** (None, Few, Many: how many islands lie off the coast). Everything else follows the seed. For an Archipelago the Islands choice is how many islands there are: Few is one island per realm, Many is many smaller ones (None is treated as Few, since an archipelago without islands is no land at all).
    - **Lakes are kept as lakes.** Water the sea cannot reach, of a useful size, stays water on the map (a place of its own, the way the sea is). Rivers can end in a lake, and **every lake has a river running out of it to the sea**, even if that is more rivers than the River count asked for. Settlements and roads stay off the water. Tiny hollows are still filled in.
    - **Steps, each ending with a check-in:** (1) the four shapes: Island out and Archipelago and Peninsula in, better Continent and Coast, a capital on each island of an archipelago (one realm per island when Few), saved worlds still opening; (2) the Coastline setting, with bays, headlands and capes; (3) the Islands setting, islands off the coast; (4) lakes with outflow rivers. Each is checked by tests (what the land is, not how it looks) and by looking at the preview in Generate World, which is where the look is judged.
  - **Later, realm borders:** realm borders that follow rivers and ranges more closely, and more control over where the land lies (for example drawing the land), moved here from the old land-shapes note. Not specified.
  - **Later, vector map styling:** choose how a vector map looks from a range of styles (for example a fantasy parchment map with hand-drawn lines and icons, a plain survey look, a dark look like the current one), set for the map or the world. A style covers the colours, line weights and fills of every place type, the background, and labels. It also has to deal with **pins**: how a place's pin looks (shape, size, icon, colour, or none), and what a pin stands for when many places overlap. A quarter, a landmark, a street and a building are different kinds of thing, and today they are all drawn and labelled in much the same way; quarters should read as areas with a label across them, not as pins like buildings, and small buildings might show only when zoomed in. Not built yet.
  - **Later, vectorising an uploaded map:** turn the features of an uploaded map image (coastlines, rivers, roads, forests, mountains, towns, walls) into vector places on the map, so they can be selected, restyled, linked to and used by the generators, instead of staying part of a picture. This would trace outlines and lines from the image, perhaps with the user choosing what each colour or symbol means and correcting the result by hand, and keep the original image behind it. Not built yet; it needs its own plan.
    - **Cells:** the settlement (inside the outline if there is one) is cut into irregular cells, which are the wards. The Streets choice decides where the cells go: a jittered grid (Planned), rings and wedges (Radial), or relaxed random points (Organic). The cell edges are the streets, so junctions, T-junctions and bends come from the cells.
    - **Gates and the main square:** the creator can place them on the preview. A gate is stored as a bearing from the middle, and the square as an offset from it in fractions of the radius, so they survive a new seed or a new size. With none placed, sensible ones are chosen.
    - **Streets:** the main streets run from each gate to the main square along cell edges (shortest path), and the other cell edges are side streets. Edges are joined along their straightest continuation into long, named streets, so there are tens of roads and not hundreds of fragments. Roads continue outside each gate as the way to other settlements.
    - **Quarters the creator chooses:** a picklist (market, wealthy, merchants, craft, slum, temple, military, gardens, harbour when there's a river). Each cell is given a type by simple rules: wealthy near the square, slums at the edge, craft near the gates and water, the temple near the square. Buildings take their look and density from the quarter they are in, and the quarter is named and made a District place.
    - **Landmarks the creator chooses:** a picklist (cathedral, castle or keep, university, library, guildhall, arena, infirmary, wizard's tower and others). Each takes a fitting cell or plot (the castle against the wall, the cathedral by the square) and becomes a named place of the new type **Landmark**, drawn in its own style.
    - **Buildings:** each cell, set back from its streets, is cut into plots with frontage on a street by repeated bisection, and a building fills each plot. They are tight in the centre and looser at the edges, and the outskirts can hold gardens and fields.
    - **Kept:** the options sheet and its preview, the seed, the outline handling, the background layout with progress, regeneration that keeps what was edited, and the export of the options.
    - **Steps, each tested and shown in the preview before the next:** (1) cells, gates, the square and streets; (2) plots and buildings; (3) quarters; (4) landmarks; (5) placing gates and the square on the preview.
  - **15c, worlds:** land and sea, regions, forests and mountains, rivers and roads, and settlements as places. The user gives the **locations** to include (cities, towns and villages, by name and kind) and the **average distances** between them, and the **terrain** (mountains, forests, rivers, seas and so on), and the generator lays them out to fit: distances as targets that it satisfies as closely as it can, terrain as areas and lines that the settlements keep clear of or sit beside as suits their kind. **Routes** are found by cost: each kind of ground has a cost to cross (a road is cheap, open land dearer, forest and hills dearer still, mountains and water barred except by a ford or bridge), and the route between two settlements is the cheapest path over it, with roads sharing where they can. At world scale the ward-and-block polygons used for a settlement are probably too artificial, so terrain and routes are better as smooth areas and curves over a cost map, with polygons only where the user draws or asks for an outline; this is to be settled when 15c is planned.
  - **15c, how the world generator works (decided):** a **Generate World…** sheet on the world map (offered when the world has no map or only a generated one), run off the main thread with progress, saving its options with the map so it can be made again, and replacing the places it made except any that were edited. The options are: the **width** of the world (default 600 km, shown in the world's unit), a **seed**, the **shape** (continent, coast or island), the number of **realms** (each has a capital city), the average **distance between** cities, towns and villages, how much **mountain** and **forest** there is, the number of **rivers**, a list of **locations** (name, kind, whether it is a capital, and optionally a spot tapped on the preview), and whether to include the settlements already on the map. It works on a coarse grid: a seeded height field with the shape's falloff and a sea level chosen to give the right share of land; mountains from the highest and most ridged ground; forest from wet low ground; rivers that start in the highlands and follow the way water runs to the sea, joining where they meet. Capitals are spread out by farthest-point choice (or taken from capitals the user listed), and each land cell belongs to the realm whose capital is cheapest to reach, so borders fall along mountains and rivers. Other settlements are dropped at random, favouring coasts and rivers, keeping their spacing and staying off the sea and mountains. Roads are the cheapest routes over a cost map (forest, hills and mountains dear, rivers dear except where a road already crosses, the sea barred): capitals first, then each city, town and village joins the nearest road or settlement already joined, so roads share. The sea is one Water polygon, each realm a Region polygon, forests and mountains polygons, rivers and roads smooth lines, and settlements pins (Settlement points), all made as children of the world with the parent chosen by the generator so nothing hides anything else. Settlement maps are made later with Generate Settlement, or the user adds settlements by hand.
  - **15d, scenes (decided):** a **Generate Scene…** button on a place that has a position, beside Generate Settlement. It makes a scene map (a vector map on the grid of 5-foot squares, ten pixels to a square, so a square is exactly 1.524 m) with a place for each part: **rooms** and **corridors** as polygons with corners on the square edges, and **doors** and **stairs** as points on the edges and in the rooms. Walls are not separate places: rooms and corridors have a heavy dark outline from their style. There are three kinds. A **dungeon** cuts the map into regions with a room in each, joins sibling rooms by L-shaped corridors (one or two squares wide), adds a few loops, and puts a door where each corridor meets a room (some secret, if asked). A **cave** evens out random cells into chambers and passages, keeps the biggest connected floor, and draws it as a smooth outline with the rock left standing in it. A **building** lays rooms either side of a central hall inside a footprint (the bounding box of the place's outline, if it has one), with a door from each room to the hall, an entrance, and optionally secret doors between rooms. Options: kind, size in squares (up to 100), how many rooms, corridor width, loops, secret doors, stairs, and the seed. The options are saved with the map and exported; it is made off the main thread with a preview, replaced when made again except edited places. New place types Room, Corridor, Door, Stairs, Cave and Rock have styles. Rooms are named by number and size ("Room 3", a large chamber); doors say which room they open into.
  - **15d, buildings, outlines and outdoor scenes (built):** a place that is a **Building** can't have a settlement map (it is already as small as one gets) and its scene defaults to the **Building** kind. The building's scene fills the building's own outline: the map is made big enough to hold the outline centred on the place, the size is set by the outline and can't be changed (a building too big for the biggest scene is shrunk to fit), and the layout copes with any shape. In a building that isn't a rectangle each room and the hall is carried on out to the outline, taking the ground nearest it (up to three squares beyond its rectangle) on a finer grid of four to a square, so rooms at a curved or slanted wall have its true shape. The grid only settles which room owns which ground: the walls come from the outline's own points (along the outside of the building a room's edge is the outline itself) and between two rooms the wall is one line that both share, so the rooms fit together with no gaps, and doors are put exactly on a room's wall. The footprint is the squares whose middles are inside the outline; the hall runs along the long way; the rest is cut into rooms as wide as the amount asked for; each room has a door to the hall, or to a room that has one, and a room that can't be reached is left out. Two **outdoor** kinds are added: a **market square** (a paved square with a fountain, stalls across it, and shops and an inn round the edge each with a door, with streets left between some of them) and a **forest clearing** (woodland, a rounded clearing, a track in from the edge of the map, boulders, a campfire, and trees crowding round but never on the clearing or the track). New place types Stall, Tree and Clearing.

### 5.10 More rule systems: modular rule systems and Daggerheart (milestones 16 and 17)

D&D 5e is one rule system among several: Daggerheart is next, and my own ruleset after it. Milestone 16 makes the app modular enough that adding a system means supplying parts, not changing the app. Milestone 17 adds Daggerheart as the first system that isn't D&D, to prove it.

- **Where D&D is built in today:** the rule system chooses the attributes shown on a page (already data-driven), but the character builder, levelling, sheet, dice, conditions, library kinds and content packs are all written for D&D 5e (they read `dnd5e.*` attributes and use a d20). A second system needs each of those to be a part the rule system supplies.
- **Milestone 16, a rule system is a set of modules:** each is independent and optional, and a system supplies only the ones it has. The screens ask what a system has and show only that, so a system with no spell slots has none, and a system with no levels has no Level Up.
  - **Attributes:** the definitions a page of each kind has (this exists).
  - **Library:** the kinds of content the system has (classes, domain cards, ancestries and so on) and the packs that fill them.
  - **Resources:** tracks with a current and a maximum value that reset on a rest or a trigger: hit points, Stress, Hope, spell slots, uses per day. The sheet, rests and slot tracking use these rather than D&D's own numbers.
  - **Rolls:** a roll model that says what dice are rolled, what is added, and how the result is read (a d20 against a target, two dice and which is higher, a pool of dice). Action cards, the dice roller and the log use it, so advantage in D&D and its Daggerheart equivalent are two readings of one mechanism.
  - **Derived values:** formulas over a character's attributes, such as modifiers, armor class, save DCs and thresholds, evaluated by one small engine, so a system adds a value by describing it.
  - **Creation and advancement:** a flow made of generic steps (choose one from a list, choose some, assign values, enter text, review) that a system composes. The D&D builder and Level Up become two compositions of the same steps.
  - **Sheet:** a layout of sections, each reading attributes and resources, with the tappable action cards.
  - **Conditions and rests:** the system's conditions and what they do to rolls, and what each kind of rest restores.
- **Data first, code where it must be:** simple modules are described in data (a rules file for the system), so a system like mine can be defined without writing Swift. A module that needs real logic (the D&D spell and slot rules) is a Swift type with the same interface, registered with the system. Both kinds sit behind the same protocols.
- **D&D 5e moves over with no change in what it does:** its builder, levelling, sheet, cards, conditions and library become modules, and the existing tests (plus parity tests that compare the new path with the old results) prove nothing moved.
- **Proving it is modular:** a small made-up rule system, defined only in data, is part of the tests. It must create a character, show a sheet, roll and rest without any D&D code, and it fails the build if a screen reaches for D&D by name.
- **Milestone 16, the order of work (decided):** each step puts one module behind an interface, with D&D as its first provider, and removes the old D&D-only code only once parity tests show identical results (the same sheets, rolls and level-ups for every SRD class, edition and level). The app can be shipped after every step.
  - **16a, the seams (built):** a `RuleModules` set on each rule system (`library`, `characterCreation`, `advancement`, `sheet`, `conditions`), and `World.rules` to ask for it. The screens that were checking for D&D or for a content library now ask for the module they need: the Build Character button, the Page | Sheet switch, the Level Up section, the Conditions box, and the library in search, mentions and the sidebar. A test reads the screens and fails if one names D&D that isn't on a list of known ones; the list only gets shorter, and each later step removes entries from it.
  - **16b, rolls and formulas (built):** a `Formula` engine (numbers, names, + − * /, brackets, floor/ceil/round/abs/min/max) and `FormulaSet` of named formulas that can use each other, plus a `RollModel` (dice, advantage as roll-twice or bonus die, critical rule, which die was higher) and `CheckRoller`. D&D's ability modifier, proficiency bonus, skill bonus and spell save DC and attack bonus now come from its formulas, with parity tests; its roll is the `.d20` model and matches the existing roller draw for draw. A Daggerheart-shaped `.duality` model (two d12s for Hope and Fear, d6 advantage, matching dice always succeed) proves the model fits. Armor class stays as it was (a stored value plus the builder's sum) and moves with the sheet in 16f. Read the Daggerheart SRD 2.0 and its licence: bundled SRD text needs the attribution line and community logo, and the licence's whitelist covers virtual tabletops, so ask Darrington Press about an app like this before 17 ships Daggerheart content.
  - **16c, resources and rests (built):** a system lists its rests and its resources (`ResourceDefinition`: the page key, whether the page keeps what remains, what is spent, or a list of spent slots, a maximum formula, and what each rest gives back: all, none, or an amount by formula, optionally only when a condition holds). D&D's hit points, temporary hit points, death saves, hit dice and spell slots are defined this way under the keys they already use, and the sheet's short and long rests are driven by them, so no character needs migrating. Not yet data: rolled amounts (Daggerheart's "clear 1d4 + tier") and exhaustion, which stays with the conditions until 16f; spending and gaining (damage, spending a slot) still live in the sheet and move with it in 16f.
  - **16d, library kinds and packs (built):** a pack can define its own kinds of entry (`entryKinds`: id, title, singular title, icon), and its entries say which with `subKind` (such as `daggerheart.domainCard`). Each kind with entries gets its own list in the Library (`LibraryList`), and copying one makes a generic `contentEntry` page ("Entries") that keeps the sub-kind in `core.entryKind` and its parts under Details. The existing kinds, the bundled packs and old worlds are unchanged. Not yet: a system saying which entry kinds its worlds show in the sidebar (`additionalPageKinds` doesn't list `contentEntry` for anyone yet), page-list screens grouping content entries by sub-kind, and a pack format version bump. These come with Daggerheart in 17.
  - **16e, creation and advancement (engine built, screens not moved yet):** a system can describe how a character is made as a `CreationFlow` (concept, choose an entry or page from a list, give out numbers by assigning from a set or freely in a range, review) with derived numbers as formulas, and how a character levels as an `AdvancementRule` (level key, maximum, gains as formulas). `CreationEngine` plans (what is missing) and creates the page, and `Advancement` levels it up. A made-up Daggerheart-shaped system in the tests builds a character and takes it from level 1 to 10 through them. D&D describes its shared steps (concept, race, class, background, abilities) and its proficiency gain as data, checked against the builder's order and `CharacterRules`; but its builder, planner and level-up screens still run the existing D&D code, so the `knownDnDScreens` list has not shrunk. Moving them onto the engine, with the D&D-only steps (skills, tools, equipment, spells; hit points and spells on level up) as extra steps the system supplies, is left until a generic builder screen exists, which 17 needs anyway. Earlier text of this step: ** generic steps (choose one, choose some, assign values, enter text, review). The D&D builder and Level Up are two compositions of them.
  - **16f, sheet and conditions (engine built, screens not moved yet):** a system lists its conditions as data (`ConditionDefinition`: effects on kinds of roll such as attack, check, save, a single save, initiative: advantage, disadvantage, auto-fail with a note, or a penalty by formula, each optionally only `when` a formula holds, with levels for something like exhaustion), and `ConditionEngine` works out what they do to a roll. D&D's conditions, in both editions, are written this way and a test checks them against the existing `ConditionRules` for 250 random states per edition across attacks, checks, initiative and all six saves. A system also gives a `SheetLayout` (sections of rows: a stat by formula, a rollable check, a resource, text, a list), `SheetEngine` works the rows out for a character page and spends or gains a resource within its limits, and a made-up system proves it. D&D's layout covers its hit points, ability modifiers and proficiency bonus, checked against `CharacterSheet`. Formula names can now contain dots, so a formula can use a page number by its key (`dnd5e.hitPoints`). Not moved: the D&D sheet screen and `CharacterSheet` (skills, attacks, spells, death saves, action cards, movement and hit-point effects of conditions) still run the existing code, so `knownDnDScreens` has not shrunk, and the generic sheet screen is built with Daggerheart in 17. Earlier text of this step: ** a sheet layout of sections that read attributes and resources, with the action cards, and conditions as a list with the effects each has on rolls.
  - **16g, a system as a data file (built):** `SystemDefinition` reads a whole system from JSON: its attributes, modules, roll model, formulas, rests, resources, creation flow, advancement, conditions and sheet layout, in plain hand-writable JSON (`type` where there are several kinds, defaults left out). `problems` checks it and says what is wrong in words (formulas that don't parse, a resource restored by a rest that doesn't exist, a sheet row showing a missing resource, repeated ids, unknown modules, attribute types or page kinds), and `DataRuleSystem` makes it a `RuleSystem`; a file with problems, a newer `formatVersion`, or a kind of thing it doesn't know is refused rather than guessed. A made-up Daggerheart-shaped system written as a file in the tests makes a character, levels it, rests it, shows its sheet and applies its conditions. Not yet: a world can't choose a data system (`RuleSystemID` is still the closed none/dnd5e, so a data system stands in as `.none`), nothing loads system files from the app or the user, and the file format has no export or editor. Worlds choosing any system, and the rest of the system's identity (versioning, export and import of the system a world uses), is 16h. Earlier text of this step: ** a JSON rules file loaded into the same modules, and a made-up test system with no D&D code that creates a character, shows a sheet, rolls and rests.
  - **16h, versioning and portability (built):** a world stores its system as a key (`systemRaw`, already a string, so no change to what is stored for D&D worlds) and records the version of the system it was last set up or imported under (`systemVersion`, a new defaulted field, 0 for existing worlds, which count as current). `RuleSystems.system(forKey:)` finds the app's own systems or one read from a file in the `SystemRegistry` (files named `*.system.json` in the app bundle are loaded the first time they are needed; none ship yet), and a key the app doesn't have is kept as it is, with the core attributes only, nothing lost, and `systemStatus` saying `.unknown`. `SystemDefinition.version` is raised by an author when the rules change, and a world can say its system has `.updated` or is `.newerThanApp`. The world pickers list every system the app has, a world keeps showing a system the app doesn't know, and the system key and version go through export and import (files without a version import as current). Not done: nothing shows the status to the user yet, a system can't be loaded from outside the app bundle (user rules files are 18), and an exported world doesn't carry the system's rules, only its key and version. Earlier text of this step: ** a world records which system and version it uses, kept through export and import.
  - **After 17, which screens are generic (decision):** the shared screens no longer name D&D: library lists and entries, page fields (a score's modifier by the system's own formula) and the sidebar ask the world's system (`libraryDetail(for:)`, `libraryAttributeLabels`, `scoreRange`, `libraryEditions`). The generic builder, sheet, rest and level-up screens run any data-defined system. D&D's own builder, level-up and sheet (and the engines behind them) stay D&D's, as the only entries left on the `knownDnDScreens` list (4 files), because moving them would mean re-expressing in data D&D's three ways of setting scores with race and background bonuses, skills, tools, equipment and spell choices limited by class, hit-point rolls, ability score improvements and feats, spell slots and preparation, death saves and the action cards: about 4,000 lines of tested code, with no change in what the app does, and no way here to look at the result. Revisit if a third system needs one of those parts, or when D&D's screens change next.
  - **Decisions:** simple modules are data (JSON, validated on load) and logic-heavy ones (the D&D spell and slot rules) stay Swift behind the same interface. Bundled systems only for 16 and 17. User-supplied rules files come with 18.
- **Rule systems are versioned and portable:** a system's attributes keep their own key prefix, so a world can change system, as D&D worlds can today, without losing what was stored. A world records which system and which version of it it uses.
- **Daggerheart differences to handle** (to be confirmed against the Daggerheart SRD, which I'll read first, including its licence and the attribution it needs):
  - Rolling uses two dice of different colours (Duality Dice) rather than a d20, so a roll has a total and also says which die was higher (Hope or Fear), and a critical is two matching dice. Advantage and disadvantage add or subtract a smaller die rather than rolling twice.
  - Characters have six traits rather than ability scores, with no proficiency bonus or skill list. Experiences take the place of skills.
  - Classes, ancestries, communities and domain cards are the content, instead of classes, species, backgrounds and spells. A character has a loadout of domain cards and a vault of those not in use, and no spell slots. Abilities are paid for in Hope and Stress.
  - Hit points and Stress are tracks to mark, with damage thresholds that decide how many hit points an attack takes, and armor is slots that are marked off.
  - Levelling follows tiers (levels 1 to 10 in groups) with choices at each level, not a class table of slots.
  - Rests and their downtime moves differ, and so does the list of conditions.
- **Existing features that change with it:** the roll cards and dice roller, the sheet, the builder and level-up flows, conditions, search and the library's lists, the content converter (a new source, with its own format), and import and export of a world's rule system. The timeline, maps, places and campaigns are unaffected, since they don't depend on the system.
- **Data stays portable:** each system's attributes keep their own key prefix (`daggerheart.*`), so a world can change system, as D&D worlds can today, without losing what was stored.

### 5.11 My own ruleset (milestone 18)

A custom TTRPG ruleset, written up in Notion and exported, as a rule system of its own.

- **Starting from the export:** I'll read the Notion export first (the markdown and CSV files and any images) and propose how it maps onto the app: its attributes, the kinds of page it has (classes, items, spells or whatever it calls them), its dice, its character creation and advancement, and its sheet. Nothing is built before that proposal is agreed.
- **Data-driven:** where the app's rule-system parts (milestone 16) allow, the ruleset is described in data, not code, so it can be changed by editing a file. A rule system file would define the attributes, the dice and how a roll reads, the library kinds and their content, and the sheet layout.
- **Content import:** the ruleset's own content (the Notion pages and tables) is converted into a content pack by a tool in the repository, like the SRD converters, so the text is copied and not retyped.
- **Open choices:** whether the ruleset stays private to me or is shipped as a bundled system, and how much of it is expressed in data and how much in code. Both depend on what the export holds.

**Status: parked (2 November 2026).** The rules need developing further before they are built. Nothing of the ruleset is implemented; this records what was found and decided so it can be picked up.

- **What the Notion export holds (Virtuous Realms, "an RPG engine" with settings called Realms):** six attributes in three virtues (Body: Strength and Agility; Mind: Intuition and Knowledge; Soul: Resolve and Charm), where at level 1 the two attributes of a virtue add up to 10; two resilience pools, Endurance (attack die d20, defence class from Strength, maximum points Resolve + Strength + Knowledge, boosted by armour and shield) and Composure (d12, defence class from Agility, maximum points Charm + Agility + Intuition, boosted by magical protection); four damage types (Injury and Strain, Mortal; Blight and Unravelling, Magical); rolls of d20 + attribute + skill level against a difficulty; six reputation spectrums that don't level up; 9 species; 29 skills (8 combat, 21 non-combat; Esoteric or Worldly) with four ranks (novice, adept, expert, paragon) and five schools of magic; 8 weapons; 5 distance bands; 5 realms; and unfinished sections (rests, group status, reactions, archetype roles, civilisation types, levelling numbers, weapon impact).
- **Decisions so far:** skill rank bonuses are novice 0, adept +1, expert +2, paragon +3, held as one editable table. Levelling gives a pool of attribute points per level for the player to spread across virtues, with the count a setting. A realm is a world option chosen when making a world and does not filter content. "Wordly" means "Worldly".
- **Suggestions made, not agreed:** defence class as a base plus the attribute plus boosts (Endurance 10 + Strength, Composure 7 + Agility, because a d12 averages four lower than a d20); the attacker rolls the die of the pool they attack; 2 attribute points and one combat and one non-combat skill step per level, a level cap of 10 and an attribute cap of 12; weapon impact dice from d4 (dagger) to d8 (sword, axe, crossbow, longbow), all dealing Injury; a spell card of shape (Snipe, Grenade, Stab, Sweep) by school, with the element as flavour and as the opposed pair, and Blight or Unravelling deciding the pool hit.
- **Engine gaps the ruleset would need:** numbers assigned in groups with a fixed sum, skills with ranks and slot rules at creation, a roll die that depends on the target, conditions that switch on by themselves (a pool at zero), spectrum attributes, and a world option for the realm.
- **To settle first:** how defence class is worked out, which die is rolled against Composure, weapon impact and damage, the spell design, and the levelling numbers.

    Pages/        list, detail, editor, attribute form

  Shared/         components, extensions
encounterTests/   Swift Testing: models, link syncing, journey derivation, search

SwiftUI views read from `@Query` and `@Environment(\.modelContext)`. Logic that is more than trivial (link syncing, journey derivation, hierarchy validation) lives in plain Swift types that are unit-testable without UI.

### JSON format notes
- Top-level `formatVersion`, so older files can still be read.
- Records reference each other by stable UUIDs, so links, hierarchy and positions survive a round trip.
- Worlds are exported as a package (`.encounterworld`, a directory with `world.json` and `images/`) so files stay small and readable. It will be declared as a document package type.
- Import creates a new world by default and never overwrites an existing one silently.
- Round-trip tests (export, import, compare) are required for every model added.

**As built (milestone 4):**
- `world.json` holds plain `Codable` records (`WorldArchive` and friends), separate from the SwiftData models. `formatVersion` is 1. Fields added later should be optional so older files still decode, and a file with a newer version is refused with a clear message.
- Page notes keep their formatting. Thumbnails aren't exported, and are regenerated on import.
- Imports always create a new world, with fresh IDs for every record. A name clash gets a suffix ("Name (2)"). A link to a missing page, or an image that is missing or can't be decoded, is skipped and counted in the summary the user sees.
- Imports repair a parent loop in a file, and a missing or duplicated default image.
- The `.encounterworld` type is declared as an exported type in the app's Info.plist (conforming to `com.apple.package`), and the app's sandbox can read and write files the user picks.
- Library references (milestone 6) will be stored as keys, not content.
- `Samples/make-sample-world/` regenerates the sample world. It is compiled against the app's own format types and checks its own output, so the sample can't drift from the format.

## 9. Decisions Made

1. **Minimum OS:** 27 and later on all platforms (raised from 26 to use SwiftUI's drag-to-reorder).
2. **Worlds:** the top-level container. A creator can have several, each with one rule system.
3. **Dates:** custom in-world calendars in v1. The creator sets hours per day, the number of months, days per month (editable per month) and month names. Years are fixed length, with no leap rules.
4. **Characters:** playable, NPCs and monsters share one form and attribute set. A playable / non-playable flag distinguishes them, so playable characters can get extra attributes later. Monsters and friendly animals are non-playable characters, told apart by a creature type attribute only, with no separate filter.
5. **Images:** pages hold multiple images, one of which is the default.
6. **Import/export:** JSON, also used to create initial test data. The format is a `.encounterworld` package (a folder holding `world.json` and `images/`).

7. **D&D content and character builder:** both are in scope for v1 (sections 5.6 and 5.7, milestones 6 to 8, with 7a to 7e building the library kinds and then the builder).
8. **Editions:** both SRD editions (5.1 and 5.2) are bundled, and each world chooses which one it uses.
9. **Content delivery:** a shared, read-only library bundled with the app. Creators can make editable custom versions of any entry in their own world.
10. **Class kind:** Class is a new page kind. Its sidebar category shows when the world's rule system has classes or the world already has class pages. (My recommended default. It only affects what the sidebar shows, so it's easy to change.)
11. **Traits and features:** structured entries (name, description, level) on the page or library entry, not separate pages.
12. **Builder scope:** level 1 first (milestone 7e), including skills, equipment, spells and backgrounds, which need those kinds in the library first (7a to 7d). Levels 2 to 20 follow in milestone 8.
